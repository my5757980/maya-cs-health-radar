## Summary

Build the Smart Customer Success Agent as a **native.builder project** (Vite + React web app,
agent-generated) backed by **Supabase** for Postgres, Auth, and Edge Functions, published to a
public `*.nativelyai.app` URL.

The health score is computed by **deterministic TypeScript in the client/DB layer** — no model
call. The agent layer runs in **two Supabase Edge Functions** that call the Anthropic API with the
key held in Supabase secret storage: one lightweight enrichment call on manual signal injection,
and one **combined structured generation call** that produces the risk explanation, the taxonomy
action, and the outreach draft in a single round trip. Collapsing spec capabilities A2–A4 into one
call is the single most important latency decision in this plan — three sequential calls would not
fit the ≤20s generation budget (NFR-4) and would triple failure surface.

**Phase 0 resolved the constitution's deferred TODO.** native.builder's documented capability set
covers everything this product needs natively, so the projected escape-hatch usage is **0% against
a 20% budget** (see [research.md](./research.md)).

### Three load-bearing architectural decisions

**AD-1 — The score never touches a model.** `scoring.ts` is pure, synchronous TypeScript. Same
signals → same score, always. This is what lets a judge watch Flow 3 and verify cause→effect
instead of taking our word for it, and it keeps the workspace render inside NFR-3 with zero
network round trips.

**AD-2 — A2+A3+A4 collapse into one structured generation call.** The explanation, the taxonomy
action, its justification, the confidence, and the draft subject/body all come back from a single
`generate-assessment` invocation returning one JSON object. Three sequential calls would spend
~30–45s against a 20s budget (NFR-4), triple the failure surface (E3), and burn three times the
tokens. One call also lets the model reason about action and message *together*, which is where
draft quality actually comes from.

**AD-3 — Model access is server-side only, via Supabase Edge Functions.** BYOK in native.builder
unlocks models in the *builder's own chat picker* — it does not give the generated app a runtime
model client. The generated app therefore calls Anthropic from an Edge Function with the key in
Supabase secret storage. This keeps the key off the client, and because the Builder agent generates
the Edge Function inside the project, it is **not** an escape hatch under Principle I.

## 3. Agent Roles Inside the App

Two categories, and conflating them is the most common way to misread this plan.

### 3a. Build-time agents (native.builder's own — they write the app)

| Agent | Role here |
|---|---|
| **Product Architect** | Consumes the scoped brief at step 2 and plans project structure before code generation |
| **Builder agent** | Generates all screens, the schema, `scoring.ts`, and both Edge Functions; iterated through chat |

These do not run in production. They are the factory, not the product.

### 3b. Runtime agents (inside the deployed app — they serve Maya)

| ID | Name | Trigger | Model | Input | Output | Budget |
|---|---|---|---|---|---|---|
| **A1** | `enrich-signal` | Manual signal injection only (seeded signals are pre-enriched at authoring time) | `claude-sonnet-5` | Signal type, severity, raw description, account name | One-phrase summary (≤ 12 words) | ≤ 3s |
| **A2+A3+A4** | `generate-assessment` | Account enters Watch/Critical, or any new signal on a Watch/Critical account, or manual regenerate | `claude-opus-5` | Account context + up to 12 most-weighted signals + dominant risk driver + the 6-action taxonomy | Single JSON: `explanation`, `cited_signal_ids[]`, `action`, `action_justification`, `confidence`, `draft_subject`, `draft_body` | ≤ 17s |

**Runtime guardrails, enforced in the Edge Function — not in the prompt:**

| Guard | Enforcement |
|---|---|
| G1 — ≥ 2 cited signals | Reject the response if `cited_signal_ids.length < 2`; retry once; then return `insufficient_signal` status (E2) |
| G1b — citations must be real | Every returned ID must exist in the signals passed in. Any unknown ID ⇒ treat as fabrication, reject (G4) |
| G4 — no invented facts | Prompt supplies a closed context; the function validates that cited IDs are a subset of supplied IDs. Prose-level fabrication is caught by the D4 10-output review |
| E4 — taxonomy bound | `action` must be one of the 6 enum values; otherwise retry once, then fall back to the driver's default action with `confidence: "low"` |
| E3 — timeout | 25s hard timeout in the function; client shows a retry control |
| S1 — no transmission | No email/HTTP-out client exists in the codebase. Enforced by absence |
| S2 — no destructive autonomy | Edge Functions hold no service-role write access to `accounts` or `signals`; they read context and return JSON. The client writes the result |

**Deterministic layer (not an agent, stated here to prevent scope drift):**

```text
penalty(signal) = base_weight[type] × severity_mult[severity] × decay(age_days)
decay(age)      = max(0, 1 − age/90)
severity_mult   = { low: 0.5, medium: 1.0, high: 1.75, critical: 2.5 }
base_weight     = { usage_drop: 15, billing_event: 14, nps_response: 13,
                    support_ticket: 12, external_event: 11, login_gap: 10,
                    feature_adoption: 8 }
                  \ external_event ADDED 2026-08-06 (Bright Data). Weighted 11 — meaningful
                  \ but below behavioral signals, because it is contextual evidence about the
                  \ company, not observed behavior inside our product.
score           = clamp(100 − Σ penalty, 0, 100)          // per-type-per-day cap: 2 signals (E6)
tier            = score ≥ 70 ? Healthy : score ≥ 40 ? Watch : Critical
stale           = no signal within 90 days ⇒ tier = Stale, not Healthy (E5)
dominant driver = signal type with the largest summed penalty
```

**Seed-tuning requirement for Flow 3:** the live-injection target account MUST be seeded to land at
**71–76** so that one injected `critical` `support_ticket` (−30) produces a visible Healthy→Watch
tier change and a re-rank on camera. Without this, the most persuasive 20 seconds of the demo
lands flat.

## 5. Data Storage Approach

**Supabase Postgres.** Full schema, constraints, indexes, and RLS in
[data-model.md](./data-model.md). Design posture:

- **Signals are append-only.** They are evidence. Nothing in the app updates or deletes a signal — this is what makes the timeline trustworthy.
- **`health_snapshots` is an audit log, not a cache.** Every score computation writes a row with its contributing signals and the triggering signal. "Why is this 34?" is answerable by query, which is the whole point of AD-1.
- **`recommendations` carries a status enum** (`pending` | `approved` | `edited_approved` | `rejected`) and a `snapshot_id`, which is how E7 staleness is detected: if the account's newest snapshot ≠ the recommendation's snapshot, warn before approving.
- **`timeline_events` is a materialized projection**, written at the same time as the source row rather than derived at read time. Costs a little write duplication; buys a single indexed read for the timeline screen and removes a 4-way UNION from the hot path.
- **`v_account_workspace`** is a view joining each account to its latest snapshot and pending-recommendation state, so the Workspace screen is one query (NFR-3).
- **`is_demo_data`** on `accounts` and `signals` drives the CF-9 badge. Honesty is a column, not a comment.
- **Seed data lives in version control** as `seed-data.json`, uploaded to the project — so a corrupted database is a 2-minute reseed, not a lost day.

**Not used:** Supabase Storage (no file uploads in-product), Realtime (single user; a refresh after
mutation is sufficient and cheaper to build), and pgvector (no retrieval in scope).

## 6. Authentication

**Decision: Supabase Auth with a single pre-provisioned demo account, auto-signed-in on load.**

| Aspect | Decision |
|---|---|
| Mechanism | Supabase Auth, email+password, one seeded user (`maya@demo.invalid`) |
| Judge experience | The app signs in with the demo credential on first load. **A judge opening the public URL lands directly in Maya's book — zero clicks, zero signup.** This is what protects SC-001's 60-second budget |
| Why auth at all | RLS needs an authenticated role to be meaningful, and Supabase's generated policies assume it. Removing auth entirely means either public-anon table access or no RLS — both worse |
| Login screen | Not built. There is no signup, no password reset, no session management UI |
| RLS | Every table is scoped to the owning CSM's `user_id`. Policies are real, not permissive-all |
| Multi-user | Explicitly out of scope (spec §12). The schema carries `user_id` so it is *possible* later, not *supported* now |

**Rationale:** a judge with a 3-minute attention budget must not meet a login wall. Auth exists to
make RLS honest, not to gate the demo. This is stated in the submission rather than hidden — a
single-demo-user posture is a legitimate hackathon scope decision; a fake login screen would not be.

**Note:** the platform automatically configures Supabase to accept builder preview URLs for auth
during development, so preview-vs-published auth behavior should not diverge. Verify at step 4.

Re-evaluated after Phase 1 artifacts were produced. **Result: PASS, no new violations.**

Two items worth stating plainly rather than burying:

1. **Anthropic API is a direct external call, not a native.builder feature.** It is made from an

   integration, with the key in Supabase secret storage. Constitution Principle I budgets escape
   hatches for things *built outside native.builder*; this is built inside it. **Not counted as an
   escape hatch** — and this reasoning is recorded in `docs/escape-hatches.md` so the judgment is
   auditable rather than assumed.

   if it is not done first.

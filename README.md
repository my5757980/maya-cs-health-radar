## What it is

A Customer Success Manager owns 60–120 accounts and can actively manage about 15 a week. Churn is
decided in the other 85.

This agent watches every account, scores health from accumulated signals, explains **why** an
account is at risk in plain language citing the specific evidence, recommends the next action, and
drafts the outreach message that executes it — then stops and waits for the human to approve.

## The one workflow

```
signal recorded → health recomputed → grounded risk explanation
    → action + drafted message → human approves / edits / rejects
    → decision written to the account timeline
```

## The design decision worth explaining

**The health score is computed by deterministic TypeScript, never by a model.**

```
penalty(signal) = base_weight[type] × severity_mult[severity] × decay(ageDays)
decay(ageDays)  = max(0, 1 − ageDays/90)
score           = clamp(round(100 − Σ penalty), 0, 100)
tier            = score ≥ 70 healthy · ≥ 40 watch · else critical
                  (no signal in 90 days ⇒ stale, regardless of score)
```

The same signals always produce the same score, so cause and effect can be verified live rather
than taken on trust. The model is used only where it genuinely beats rules: reading heterogeneous
signals into a coherent narrative, choosing a fitting action, and writing the message.

**Grounding is enforced in code and schema, not in the prompt:**
- Every explanation must cite **≥ 2 real signals** — a Postgres CHECK constraint makes an ungrounded recommendation impossible to save
- Cited signal ids are validated server-side as a **subset of the context actually supplied** — an invented citation is rejected, not filtered out
- Actions are bounded to a **six-value Postgres enum**; out-of-taxonomy output retries once, then falls back to the driver default at low confidence
- `signals` is append-only (SELECT + INSERT only) — evidence is immutable, so the timeline is trustworthy

**Nothing is ever sent.** Approval records the decision and the final message text. There is no
email client, no SMTP config, and no outbound sender anywhere in the codebase — the safety boundary
is enforced by absence, not by a flag.

## Demo data

10 fictional accounts — 2 critical, 3 watch, 1 stale, 4 healthy — labeled as demo data in the UI.
No real customer data.

**Live demo moment:** *Acme Dashboard* is seeded to score exactly **72 (healthy)**. Adding one
critical support ticket drops it to **42 (watch)** — a ~30 point swing that recomputes the score,
flips the tier, re-ranks the account, and regenerates the assessment citing the signal created
seconds earlier. Nothing is pre-recorded.

## Running it yourself

```bash
npm install
npm run dev
```

You will need your own Supabase project and an `AIML_API_KEY` secret for the Edge Functions.
Schema and seed data live in the Supabase project, not in this repo — see `data-model.md` for the
full schema, constraints and RLS policies.

## Deploying

There is no separate backend server to host. The frontend is a static Vite build; everything
server-side — Postgres, Auth, and the three Edge Functions — already runs on Supabase.

So a single static host is all that is needed. `vercel.json` sets the Vite preset and a SPA
rewrite, so `/account/:id` survives a direct link or a refresh instead of 404ing:

```json
{ "rewrites": [{ "source": "/(.*)", "destination": "/index.html" }] }
```

Point any static host at the repo, or:

```bash
npm run build   # -> dist/
```

Nothing to configure at deploy time: the Supabase URL and **anon** key are compiled into the
bundle, which is what that key is designed for — row-level security is what actually protects the
data, not key secrecy. The `AIML_API_KEY` never reaches the browser; it lives in Supabase Secrets
and is read only inside the Edge Functions.
